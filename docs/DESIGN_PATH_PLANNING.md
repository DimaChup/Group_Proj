# Path Planning Design

This document describes the search pattern generation and path planning subsystem of the SAR drone. It covers the algorithmic choices, geometric optimisations, and operational parameters implemented in `planning.py`, `config.py`, and `state_machine_no_descend.py`. All numeric values cited below are drawn directly from the codebase.

---

## 1. Lawnmower Pattern Selection

The system uses a boustrophedon (lawnmower) scan pattern as the primary search strategy. Three alternative patterns were considered:

| Pattern | Coverage guarantee | Complexity | SAR precedent |
|---------|-------------------|------------|---------------|
| **Lawnmower** | Complete (every cell visited) | Low | Standard in maritime and land SAR |
| Expanding spiral | Biased toward centre; edges under-covered | Medium | Used when POI is estimated |
| Sector search | Requires known last-seen point | Medium | Coast Guard creeping line variant |

The lawnmower pattern was selected for three reasons:

1. **Complete coverage guarantee.** Every point inside the polygon is swept at least once, regardless of polygon shape. This is critical when no prior information about the casualty location exists.
2. **Implementation simplicity.** The pattern reduces to generating equally-spaced horizontal scan lines across a rotated polygon, a well-understood computational geometry operation.
3. **Proven SAR literature basis.** Boustrophedon decomposition is the standard coverage path planning method recommended by JSAR (Joint Search and Rescue Manual) and is widely used in autonomous marine and aerial SAR platforms.

### Binary mask approach

The planner handles arbitrary polygon shapes, including concave boundaries, by rasterising the search polygon onto a binary mask using `cv2.fillPoly`. Scan lines are then generated by reading non-zero pixel runs from each row of the mask. This avoids the need for explicit polygon clipping algorithms and naturally handles concave regions, holes, and irregular boundaries. The mask resolution is set by the map's pixel-per-metre scale (`GeoTransformer.pix_per_m`), which is derived from the satellite image and reference coordinates.

## 2. Scan Angle Optimisation

The polygon orientation relative to the scan direction affects the number of scan lines and therefore total flight time. The planner determines the optimal scan angle using the minimum-area bounding rectangle of the polygon (`cv2.minAreaRect`). The scan direction is aligned with the longest edge of this rectangle, which minimises the number of perpendicular scan lines needed to cover the area.

Specifically, the `minAreaRect` returns `(center, (w, h), angle)`. The planner selects:

```python
scan_angle = angle + 90 if size[0] < size[1] else angle
```

This ensures the scan lines run parallel to the longest dimension of the bounding rectangle.

### Exhaustive analysis

A comprehensive path optimisation analysis was conducted across 6 altitudes (20 m, 25 m, 30 m, 35 m, 40 m, 50 m) and 36 scan angles (0 to 175 degrees in 5-degree steps), totalling 216 configurations. The analysis script (`analysis/path_optimization/optimize_path.py`) evaluates each combination for path length, search time, energy consumption, and NFZ slowdown penalty.

Results show that the optimal scan angle for the AENGM0074 survey polygon falls in the 65--75 degree range, consistent with the polygon's elongated NE--SW geometry. The angle returned by `minAreaRect` agrees with this range. Plots of the full parameter sweep are saved in `analysis/path_optimization/`:

- `plot1_energy_vs_altitude.png` -- total energy with and without NFZ slowdown
- `plot2_time_vs_altitude.png` -- total search time comparison

## 3. Diagonal Realignment (53-Degree Yaw Offset)

The onboard camera produces a 1456 x 1088 pixel image (IMX296 global shutter sensor). The ground footprint is a rectangle whose dimensions depend on altitude. The key geometric insight is that the rectangle's diagonal is significantly longer than either side:

```
diagonal = sqrt(1456^2 + 1088^2) = 1818 pixels
```

By yawing the drone so that the camera diagonal is perpendicular to the flight direction, the effective swath width increases from 1088 pixels (the image height) to 1818 pixels (the diagonal). This is a factor of 1818 / 1088 = **1.67x**, providing 67% more ground coverage per scan line at zero additional flight cost. The drone follows the same path; only its heading changes.

The required yaw offset is:

```
offset = atan(IMAGE_W / IMAGE_H) = atan(1456 / 1088) = 53.2 degrees
```

This angle is configurable via `DIAGONAL_YAW_OFFSET_DEG` in `config.py`. When set to `None`, the system auto-computes it from the camera aspect ratio. When set to `0`, the drone faces along the scan direction (no rotation). The current configuration sets it to `0` (disabled), but the feature is flight-ready and can be enabled by setting the value to `None` or `53`.

At the start of the SEARCH state, the state machine orients the drone once:

```python
yaw_deg = (flight_direction + diag_offset) % 360
```

A `MAV_CMD_CONDITION_YAW` command is sent, and the search pattern does not begin until the yaw error is within tolerance.

## 4. Swath Width and Overlap

The camera ground footprint width at a given altitude is:

```
ground_width = (SENSOR_WIDTH_MM * altitude) / FOCAL_LENGTH_MM
             = (5.02 * altitude) / 5.46  [metres]
```

At the default search altitude of 35 m, this gives a ground width of approximately 32.2 m.

The ground height (perpendicular to the longer footprint dimension) is:

```
ground_height = ground_width * (IMAGE_H / IMAGE_W)
              = ground_width * (1088 / 1456)
              = ground_width * 0.747
```

In no-turn mode (the current operational configuration, `_no_turn = True`), the swath spacing uses the image height dimension (perpendicular to flight) and **0% explicit overlap** between scan lines:

```python
ground_width_m = ground_width_m * aspect  # use height, not width
overlap = 0.0
SWATH_M = ground_width_m * (1.0 - overlap)
```

The rationale for zero overlap is that the diagonal realignment already provides a 67% coverage bonus. Even without any overlap parameter, consecutive scan lines share significant ground area due to the rotated footprint geometry.

### Edge margin

A margin of 1/3 of the swath width is maintained from the polygon edges. This ensures the camera footprint does not extend significantly beyond the search boundary:

```python
margin = step_px // 3
```

In focus area mode (PLB beacon redirect), the same 1/3 margin is used but applied to a much smaller polygon, resulting in tighter absolute margins.

## 5. Altitude-Dependent Speed

Search speed varies linearly with altitude to balance detection reliability against coverage rate. The relationship is defined in `config.py`:

| Parameter | Value |
|-----------|-------|
| `SPEED_ALT_LOW` | 20 m |
| `SPEED_ALT_HIGH` | 50 m |
| `SPEED_AT_LOW` | 6.0 m/s |
| `SPEED_AT_HIGH` | 10.0 m/s |

The interpolation function (`speed_for_altitude`) computes:

```python
if alt <= 20:  return 6.0
if alt >= 50:  return 10.0
ratio = (alt - 20) / (50 - 20)
return 6.0 + ratio * (10.0 - 6.0)
```

At the default search altitude of 35 m, this yields 8.0 m/s.

**Rationale:** At lower altitudes the target subtends more pixels and is more likely to be detected, but the drone speed produces proportionally more motion blur on the rolling-shutter or global-shutter sensor. Slower speeds at low altitude ensure each frame has sufficient exposure time relative to ground motion. At higher altitudes, the target is smaller but blur is less severe because the angular rate of ground features is lower, so higher speeds are acceptable.

The focus area search uses a separate, slower speed (`FOCUS_SEARCH_SPEED_MPS = 5.0 m/s`) to maximise detection probability in the high-priority PLB region.

## 6. Rescan Passes

If the first search pass completes without confirming a target, the system automatically drops altitude and rescans. The parameters are:

| Parameter | Value |
|-----------|-------|
| `MAX_RESCAN_PASSES` | 3 |
| `RESCAN_ALT_FACTOR` | 0.8 (20% reduction per pass) |
| `RESCAN_ALT_FLOOR_M` | 15.0 m |

The altitude progression for a starting altitude of 35 m is:

| Pass | Altitude | Speed | Ground width | Scan lines |
|------|----------|-------|-------------|------------|
| 1 (initial) | 35.0 m | 8.0 m/s | ~32.2 m | Fewest |
| 2 (rescan 1) | 28.0 m | 7.1 m/s | ~25.7 m | More |
| 3 (rescan 2) | 22.4 m | 6.3 m/s | ~20.6 m | Most |

Each altitude reduction narrows the camera footprint, which increases the number of scan lines needed to cover the same area. This trades flight time for detection probability: smaller, partially-occluded, or low-contrast targets that were missed at 35 m may be visible at 22 m where the target subtends approximately 60% more pixels.

The rescan pattern is regenerated from the drone's current position at the end of the previous pass, using the new altitude:

```python
self.waypoints = self.planner.generate_search_pattern(
    canvas_w, canvas_h, (self.lat, self.lon), alt_override=new_alt)
```

Bezier smoothing is reapplied if the `--smooth-bezier` or `--smooth-extra` flags are active.

## 7. Focus Area (PLB Beacon Redirect)

When a Personal Locator Beacon (PLB) signal is received (simulated via `--beacon-delay N` flag or triggered programmatically), the search is immediately redirected to a smaller focus area polygon. The redirect logic in `_trigger_beacon_redirect()` follows a priority chain:

1. **`flight_plans/focus_area.json`** on disk (re-read each time, allowing mid-flight coordinate updates from the ground station)
2. **Drawn polygon** from the interactive map setup (stored in `config.FOCUS_AREA_GPS`)
3. **KML Focus Area** from `AENGM0074.kml` (loaded at startup)

Upon redirect:

- The planner's search polygon is swapped to the focus area polygon.
- `planner._focus_area = True` is set, which uses tighter margins (1/3 swath, same as normal, but on a much smaller polygon).
- A new lawnmower pattern is generated from the drone's current position.
- The waypoint index resets to 0 and the rescan counter resets.
- Search speed drops to `FOCUS_SEARCH_SPEED_MPS` (5.0 m/s), prioritising detection time over area coverage.
- The drone re-orients its yaw for the new scan direction before beginning the focus search.

Rejected targets (operator-marked false positives) are preserved across the area switch so they are not re-investigated.

## 8. Entry/Exit Considerations

The planner optimises the starting corner of the lawnmower pattern based on the drone's current position. Four candidate entry points are evaluated (top-left, top-right, bottom-left, bottom-right of the scan grid), and the closest to the drone is selected:

```python
min_dist = min(d_top_left, d_top_right, d_bot_left, d_bot_right)
```

This determines both the strip ordering (top-to-bottom or bottom-to-top) and the initial scan direction (left-to-right or right-to-left). The zigzag direction alternates with each subsequent scan line.

After the last scan line, the drone either:
- Initiates a rescan pass at lower altitude (if `rescan_pass < MAX_RESCAN_PASSES`), or
- Retraces the transit waypoints back to the home/landing position.

Transit waypoints are pre-planned on the interactive map and stored in `flight_plans/transit_waypoints.json`. The drone flies these at `TRANSIT_SPEED_MPS` (15.0 m/s), which is faster than search speed since no detection processing occurs during transit.

## 9. Modularity

`planning.py` is a fully independent module with no coupling to the state machine, navigation layer, or detection system. Its interface is:

```python
planner = PathPlanner(geo_transformer, search_polygon_pixels)
waypoints = planner.generate_search_pattern(map_w, map_h, drone_gps, alt_override)
```

**Input:** A polygon (as pixel coordinates) and an altitude.
**Output:** A list of `(lat, lon)` GPS waypoints in flight order.

The rest of the system treats these waypoints as an opaque sequence and flies them in order. This means a new search pattern (spiral, sector, adaptive, or any other coverage algorithm) can be added by implementing a method that returns the same `[(lat, lon), ...]` format. The state machine, navigation commands, and detection pipeline require no modifications.

A spiral pattern generator (`generate_spiral_pattern`) is already implemented as a proof of concept, using the same rotated-mask approach and returning the same waypoint format.

A Bezier smoothing post-processor (`smooth_waypoints`) is also available, inserting quadratic Bezier curve points at U-turns to allow the drone to fly smooth arcs rather than stopping at each corner. This is activated via the `--smooth-bezier` flag and is applied identically to both initial and rescan patterns.

## 10. Path Optimisation Analysis

A comprehensive analysis was conducted to quantify the energy, time, and geometric trade-offs across the full parameter space. The analysis script (`analysis/path_optimization/optimize_path.py`) evaluates 216 configurations (6 altitudes x 36 scan angles).

### Energy model

The energy model uses a simplified quadcopter power formulation:

| Component | Formula | Value |
|-----------|---------|-------|
| Hover power | Constant | 150 W |
| Movement power | `50 * (speed / 5)^2` W | Scales with speed squared |
| U-turn penalty | 2 seconds of hover-only power per turn | ~0.083 Wh per turn |

Total energy:

```
E = P_hover * t_total + P_drag * t_flight
```

where `t_total` includes scan time, transit time, and U-turn penalties; `t_flight` excludes U-turn hover periods.

### NFZ (SSSI) slowdown

The survey polygon is adjacent to a Site of Special Scientific Interest (SSSI) no-fly zone. Within 20 m of the NFZ boundary (`NFZ_SLOW_ZONE_M`), speed ramps linearly from 3.0 m/s at the outer edge down to 0.3 m/s at the boundary. The analysis computes both NFZ-aware and NFZ-unaware metrics for comparison.

The NFZ slowdown adds approximately **45% time penalty** due to the SSSI adjacency at the survey site. This is because several scan lines pass within the 20 m slow zone, where speed drops by up to 97% (from search speed to 0.3 m/s near the boundary).

### Key findings

- **Optimal scan angle:** 65--75 degrees across all altitudes, consistent with the polygon's elongated geometry.
- **Energy vs altitude trade-off:** Lower altitudes require more scan lines (narrower footprint) but fly slower, roughly doubling energy at 20 m compared to 50 m. Higher altitudes are more energy-efficient but reduce target pixel size.
- **35 m (default) is the operational compromise:** sufficient target size for reliable YOLOv8n detection (~24 pixels at 35 m based on a 1.8 m dummy), acceptable energy budget, and manageable scan line count.
- **U-turn count dominates at low altitude:** at 20 m, the swath is ~18 m, producing roughly twice as many scan lines as at 35 m.

Full results and plots are available in `analysis/path_optimization/`.
