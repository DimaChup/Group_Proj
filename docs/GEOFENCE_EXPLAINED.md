# Geofence System -- How It Works

This document explains every layer of boundary enforcement in the SAR drone system.
There are two independent boundaries: the **Flight Area** (outer box) and the
**SSSI No-Fly Zone** (inner polygon). Each works differently.

---

## 1. Flight Area Boundary (R01)

**What it is:** A 4-vertex polygon defining the maximum allowed flight envelope.
Defined in `config.py` as `FLIGHT_AREA_GPS` (loaded from `AENGM0074.kml`).

**What check is performed:**
Every main loop iteration, `_enforce_geofence()` converts the Flight Area polygon
to a cv2 contour and calls `cv2.pointPolygonTest(fa_poly, (lon, lat), False)`.
If the result is negative (drone is outside the polygon), it triggers an
emergency RTL immediately.

**What happens when the drone crosses the boundary:**
- `_emergency_rtl()` is called with reason `"Outside Flight Area boundary"`.
- This sends a MAVLink `MAV_CMD_DO_SET_MODE` command setting mode 6 (RTL).
- A loud terminal message prints:
  ```
  ============================================================
    EMERGENCY: Attempting RTL  --  Outside Flight Area boundary
    If RTL fails, ArduCopter GCS failsafe should trigger RTL
    RC kill switch is always available
  ============================================================
  ```
- The function returns immediately -- no further geofence processing happens.

**Buffer/warning zone:** There is NO buffer or warning zone for the Flight Area.
It is a hard cutoff: inside = OK, outside = immediate RTL. There is no gradual
speed reduction as the drone approaches the Flight Area edge.

**How often checked:** Every iteration of the main loop (approximately every
20-50ms depending on headless mode and detection speed). The check is skipped
during states INIT, CONNECTING, ARMING, TAKEOFF, LANDING, and DONE, and also
skipped entirely when the RC pilot has overridden control (mode is not
GUIDED or LAND).

## 2. SSSI No-Fly Zone (R02)

The SSSI (Site of Special Scientific Interest) is a 7-vertex polygon defined in
`config.py` as `SSSI_GPS`. It has **four layers of protection**, plus two speed
clamping modes. Each layer is described below with exact distances from `config.py`.

### Config Parameters (from `config.py`)

| Parameter | Value | Meaning |
|-----------|-------|---------|
| `NFZ_WAYPOINT_BUFFER_M` | 30 m | Plan-time: skip waypoints this close to NFZ |
| `NFZ_SLOW_ZONE_M` | 20 m | Runtime: speed reduction starts at this distance |
| `NFZ_ZONE_MAX_SPEED_MPS` | 3.0 m/s | Maximum speed at the outer edge of the slow zone |
| `NFZ_SCALAR_ZERO_M` | 2.0 m | Speed drops to 0 (full stop) at this distance |
| `NFZ_HARD_BOUNDARY_M` | 3.0 m | Force MANUAL mode at this distance (legacy, used by `check_position()`) |
| `NFZ_SOFT_BOUNDARY_M` | 8.0 m | Repulsive field activates within this (legacy, used by `repulsive_offset()`) |
| `NFZ_INNER_OFFSET_M` | 20.0 m | Inner polygon offset for repulsion trigger |
| `NFZ_INNER_RANGE_M` | 23.0 m | Repulsion active within this distance from inner polygon |
| `NFZ_PUSH_SPEED_MPS` | 5.0 m/s | Constant repulsive push speed in MANUAL mode |

### Layer 1: Plan-Time Waypoint Filtering

**Where:** `geofence.py`, method `filter_waypoints()`.

**How it works:** Before the mission starts, the lawnmower search pattern is
generated by `planning.py`. The geofence can then filter out any waypoint that
is inside the SSSI polygon or within `NFZ_WAYPOINT_BUFFER_M` (30 metres) of its
boundary.

**Important caveat:** As of the current code, `filter_waypoints()` exists in
`geofence.py` but is **not called** from `main.py`. It is tested in
`tests/flight/0e_geofence_test.py` and `tests/automated/geofence_unit_test.py`,
but the actual mission does not invoke it during waypoint generation. The
lawnmower pattern generator in `planning.py` also has no NFZ awareness.
This means waypoints CAN be generated inside or near the SSSI -- the runtime
layers (2-4) handle the protection instead.

**Terminal output when active:** `[GEOFENCE] Filtered N waypoints within 30m of SSSI`

### Layer 2: Speed Scalar Field (20m to 2m from boundary)

**Where:** `main.py`, method `_enforce_geofence()`, lines ~920-973.

**How it works:** When the drone is outside the SSSI but within `NFZ_SLOW_ZONE_M`
(20 metres) of the boundary, its speed is reduced. There are two modes controlled
by the `--nfz-total-speed` CLI flag:

#### Mode A: Directional Speed Clamping (default, `NFZ_DIRECTIONAL = True`)

Only limits the speed **component toward the NFZ boundary**. The drone can still
fly at full speed parallel to the boundary.

1. Compute the unit vector from the drone toward the nearest point on the SSSI
   boundary edge.
2. Project the drone's current velocity onto that vector (dot product).
3. If the approach component exceeds the allowed maximum, reduce speed.

The allowed approach speed ramps linearly:
- At 20m from boundary: up to 3.0 m/s approach speed
- At 2m from boundary: 0.0 m/s (full stop, cannot approach further)
- Between 20m and 2m: linear interpolation

#### Mode B: Total Speed Clamping (`--nfz-total-speed` flag)

Limits the drone's **total speed** regardless of direction:
- At 20m: up to 3.0 m/s
- At 2m: 0.0 m/s
- Between: linear interpolation

This is more conservative but can interfere with the drone's ability to fly
away from the NFZ (it slows down in all directions).

**Skip conditions:** Speed clamping is skipped during states HOVER_TARGET,
APPROACH, RETURN_TRANSIT, and RETURN_HOME (the `skip_speed_clamp` flag). This
is because speed clamping bleeds into the vertical axis via the 3D position
controller, which blocks descent and climb manoeuvres.

### Layer 3: Repulsive Potential Field (MANUAL mode only)

**Where:** `geofence.py`, method `repulsive_offset()`, applied in
`main.py` `_enforce_geofence()` lines ~975-991.

**How it works:** When the drone is in MANUAL mode (which happens after an NFZ
incursion, see Layer 4), a repulsive velocity command pushes it away from the
boundary.

**Trigger condition:** The drone must be in MANUAL mode AND within
`NFZ_INNER_RANGE_M` (23m) of the "inner polygon" (the SSSI boundary eroded
inward by `NFZ_INNER_OFFSET_M` = 20m). In practice, this means approximately
within 3m of the actual SSSI boundary.

**The push mechanism:**
1. Find the nearest point on the SSSI boundary edge (iterates over all edges,
   projects the drone position onto each edge segment, picks the closest).
2. Compute a push vector: drone position minus closest boundary point (pointing
   away from the boundary).
3. If the drone is exactly on the boundary (degenerate case), compute the
   outward normal of the nearest edge instead.
4. Scale the push by `(SOFT_BOUNDARY - distance) * 0.5` metres -- stronger
   push when closer.
5. Convert from pixel space to GPS offset with sign correction (the GPS
   conversion is inverted, so the final values are negated).
6. Send a velocity command at `NFZ_PUSH_SPEED_MPS` (5.0 m/s) in the push
   direction.

**Why MANUAL mode only:** In other states (SEARCH, CENTERING, etc.), the state
handler is already sending position targets via `send_global_target`. Sending
velocity commands on top would fight the position controller and destabilise
altitude control. In MANUAL mode, no other commands are being sent, so the
repulsive push can work cleanly.

### Layer 4: Hard Cutoff (Inside the Polygon)

**Where:** `main.py`, `_enforce_geofence()`, lines ~896-914.

**What happens when the drone is inside the SSSI polygon:**

**Normal states (SEARCH, CENTERING, etc.):**
- Prints `[GEOFENCE] INSIDE NFZ! Switching to MANUAL`
- Saves the current state as `previous_state` (for potential return)
- Saves departure position (lat, lon, alt)
- Switches state to `State.MANUAL`
- Sends a zero-velocity command `send_velocity(0, 0, 0)` to halt all motion
- The repulsive push (Layer 3) then activates to push the drone back out

**During HOVER_TARGET, APPROACH, RETURN_TRANSIT, RETURN_HOME
(`skip_speed_clamp=True`):**
- Does NOT switch to MANUAL mode
- Prints `[GEOFENCE] Brief NFZ incursion during <STATE> -- position target active, no MANUAL switch`
- Trusts that the existing position target (which is outside the NFZ) will
  naturally pull the drone back out
- This avoids disrupting descent/climb sequences with a mode switch

### Detection Filtering

There is **no detection filtering based on SSSI location**. The system does not
check whether a detected target is inside the SSSI before investigating it.
If a detection occurs while the drone is near the SSSI, the drone will attempt
to investigate, and the runtime geofence layers (speed reduction, hard cutoff)
will prevent it from entering the NFZ.

### Landing Spot Safety

When choosing a 7.5m offset landing spot after target confirmation, the system
checks if the landing position is too close to the NFZ (within 15m). If so, it
tries all four cardinal directions (N, S, E, W) and picks the one furthest from
the NFZ boundary. This prevents landing near or inside the SSSI.

## 3. What the Pilot/Operator Sees

### Terminal Messages

| Situation | Message |
|-----------|---------|
| Startup (NFZ active) | `[GEOFENCE] SSSI NFZ active -- 7 corners, hard=3.0m, soft=8.0m` |
| Startup (Flight Area) | `[GEOFENCE] Flight Area geofence: 4 vertices (R01)` |
| Outside Flight Area | `EMERGENCY: Attempting RTL -- Outside Flight Area boundary` (with box) |
| Inside SSSI polygon | `[GEOFENCE] INSIDE NFZ! Switching to MANUAL` |
| Brief SSSI incursion during approach | `[GEOFENCE] Brief NFZ incursion during APPROACH -- position target active, no MANUAL switch` |
| Landing spot too close to NFZ | `[NFZ] Landing spot N is 5m from NFZ -- too close!` |
| Landing spot redirected | `[NFZ] Redirected to S (45m from NFZ)` |
| Waypoint filtering (if called) | `[GEOFENCE] Filtered 12 waypoints within 30m of SSSI` |

There are no "approaching NFZ" or "speed reduced" messages printed during the
speed scalar field operation. The speed reduction happens silently.

### Map/HUD Visualization (Simulation Mode)

The simulation god-view map shows:
- **Red polygon with semi-transparent fill:** SSSI NFZ boundary, labelled "SSSI NFZ"
- **Pink polygon (bold):** Inner NFZ polygon (20m eroded inward from boundary)
- **Orange outline:** Buffer zone ring (20m expanded outward from boundary)
- **Vector field arrows** (with `--arrows` flag): Shows repulsive force direction
  and strength at grid points around the NFZ. Colour-coded: red (<4m), orange
  (<7m), yellow (farther).
- **Bold arrow on drone:** When repulsive push is active, a large arrow shows
  the push direction from the drone's position.

The Flight Area is shown as a blue polygon outline in the dry-run visualization.

### Pilot Override

The pilot can **always** override the geofence:
- **RC mode switch:** Switching the RC transmitter away from GUIDED mode
  (e.g., to STABILIZE or LOITER) immediately causes the main loop to skip ALL
  processing including geofence enforcement (line 770: `continue`). The pilot
  has full manual control.
- **RC kill switch:** Always available regardless of software state.
- **`--no-nfz` flag:** Disables the SSSI geofence entirely at startup. The
  `NFZGeofence` object is never created and all NFZ checks are skipped.
  Flight Area containment is still checked separately in `_enforce_geofence`
  even with `--no-nfz`.

## 4. Edge Cases

### GPS Loss Near the Boundary

There is **no explicit handling** for GPS loss near the boundary. If GPS
readings stop updating, the drone's `self.lat` and `self.lon` values freeze at
their last known position. The geofence will keep evaluating against those stale
coordinates and will not detect drift.

However, ArduCopter's built-in failsafes provide backup:
- **EKF failsafe:** Triggers RTL or LAND if the Extended Kalman Filter detects
  position uncertainty exceeding thresholds.
- **GPS failsafe:** Triggers if GPS fix is lost for too long.

The software relies on these ArduCopter-level failsafes for GPS loss scenarios.

### Wind Pushing Past the Boundary Between Checks

The geofence is checked **every main loop iteration** (approximately 20-50ms,
or 20-50 Hz). At the drone's maximum speed of 5 m/s, it could travel
0.10-0.25 metres between checks -- well within the reaction margins.

However, a sudden gust could theoretically push the drone from the 2m full-stop
zone into the SSSI polygon in a single loop iteration. In that case:
- Layer 4 activates: switches to MANUAL mode
- Layer 3 activates: sends a 5 m/s repulsive push outward
- The drone should recover within 1-2 seconds

The 2m full-stop zone (`NFZ_SCALAR_ZERO_M`) provides a buffer specifically for
this scenario -- the drone should already be at zero approach speed before it
reaches the boundary.

### Geofence Check Frequency

The geofence is checked **every iteration of the main loop** (`run()` method).
It runs AFTER the state handler processes the current state and AFTER key
handling, but BEFORE the loop sleeps for the next iteration.

**States where geofence is NOT checked:**
- INIT, CONNECTING, ARMING (drone is on the ground, not flying)
- TAKEOFF (drone is climbing, brief period of unprotected ascent)
- LANDING (drone is descending to land, sending LAND commands)
- DONE (mission complete)

**Situations where geofence is skipped entirely:**
- RC pilot override (mode is not GUIDED or LAND)
- `--no-nfz` flag was passed at startup
- No SSSI_GPS configured (fewer than 3 vertices)

### The `check_position()` Method (Legacy)

The `geofence.py` file contains a `check_position()` method that returns
traffic-light status (`safe`/`warning`/`critical`) and a speed factor. This
method uses `NFZ_HARD_BOUNDARY_M` (3m) and `NFZ_SOFT_BOUNDARY_M` (8m) for its
zone classification.

**This method is not called by `main.py`.** The actual runtime enforcement in
`_enforce_geofence()` implements its own distance checks using
`NFZ_SLOW_ZONE_M` (20m) and `NFZ_SCALAR_ZERO_M` (2m) directly. The
`check_position()` method is available for other scripts (like passive_watch)
but is not part of the main mission geofence enforcement.

## Summary: Distance Zones from SSSI Boundary

```
                                          SSSI POLYGON
                                    ========================
                                    |                      |
                            0m ---- | INSIDE: MANUAL mode  | ---- 0m
                                    | + 5 m/s repulsive    |
                                    | push (Layer 3+4)     |
                                    ========================
                            2m ---- Full stop (0 m/s approach)
                                    |
                                    | Linear speed ramp
                                    | (0 -> 3 m/s)
                                    |
                           20m ---- Slow zone boundary (3 m/s max)
                                    |
                                    | Full speed allowed
                                    |
                           30m ---- Waypoint filter buffer (plan-time, NOT active in main.py)
                                    |
                                    | Completely unrestricted
```

**Files involved:**
- `/v3/geofence.py` -- NFZGeofence class (distance calculation, waypoint filter, repulsive field)
- `/v3/main.py` -- `_enforce_geofence()` method (runtime enforcement, speed clamping, MANUAL switch)
- `/v3/config.py` -- All NFZ distance parameters (lines 120-131)
- `/v3/simulator/simulation.py` -- Visual rendering of NFZ zones on god-view map
