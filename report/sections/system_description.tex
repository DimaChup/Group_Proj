\section{System Description}\label{sec:sysdesc}

The final system comprises a hardware platform, five software layers, a computer vision pipeline, a target localisation subsystem, a browser-based ground station, and a multi-fidelity simulation framework. Figure~\ref{fig:mission_overview} shows the complete mission plan overlaid on the Fenswood Farm site.

The Pi communicates with the Cube via UART at 921\,600\,baud through a MAVProxy bridge, which re-publishes MAVLink traffic over UDP. A second output on TCP port~5762 allows Mission Planner on the ground station laptop to monitor telemetry via Wi-Fi. The camera captures at $1456 \times 1088$ via CSI-2; lens distortion is corrected using precomputed remap matrices (calibrated RMS = 0.399\,px, +1.5\,ms overhead). The calibrated focal length is \SI{5.46}{\milli\metre}, yielding a horizontal FOV of $\approx 49.3^{\circ}$.

The data pipeline traverses five stages per iteration: (1)~capture frame and apply lens undistortion; (2)~resize to $640\times640$, normalise, run YOLOv8n inference; (3)~convert pixel detection to GPS estimate; (4)~dispatch current state handler; (5)~enforce geofence constraints. Geofencing always runs \emph{after} the state handler, so waypoint commands can be overridden by repulsive velocities.

\paragraph{Geofence enforcement.}
The geofence module implements three nested protection layers (Figure~\ref{fig:geofence_diagram}): the SSSI no-fly zone (hard boundary---entering triggers automatic MANUAL mode), the flight area polygon (soft boundary---repulsive velocity pushes the drone inward), and a \SI{10}{\metre} buffer zone surrounding the SSSI where repulsive forces activate proportionally to proximity. The repulsive offset is computed using \texttt{cv2.pointPolygonTest} for signed distance and applied as a velocity correction after the state handler's waypoint command, ensuring that no state can inadvertently fly into restricted airspace.

\subsection{Computer Vision Pipeline}\label{sec:cv}

The vision subsystem is encapsulated in \texttt{vision.py}, exposing a single interface: \texttt{detect\_in\_image(frame)} $\to$ \texttt{(found, cx, cy, confidence)}. The pipeline proceeds as follows:

\paragraph{Preprocessing.} Lens undistortion (if calibration data available), colour space handling (IMX296 outputs BGR despite RGB888 label---no conversion applied), resize from $1456\times1088$ to $640\times640$ via bilinear interpolation, and float32 normalisation ($[0,255] \to [0,1]$) yielding input tensor $[1, 640, 640, 3]$.

\paragraph{Inference.} The TFLite model produces output tensor $[1, 5, 8400]$ (8400 anchor-free candidates across three feature pyramid scales). Postprocessing: confidence filtering (threshold 0.2), best-detection selection (greedy single-target), and coordinate rescaling to original frame dimensions. The Ultralytics backend handles NMS internally; TFLite implements equivalent filtering in \texttt{vision.py}.

\paragraph{Three backends.} The system supports Ultralytics~\cite{yolov8} (development laptop) and TFLite~\cite{tflite} (production Pi), with an NCNN~\cite{ncnn} backend implemented but not yet benchmarked on the Pi. Backend selection is automatic at import time. Both validated backends consume the same model weights and produce identical detection semantics.

\begin{figure}[ht]
\centering
\includegraphics[width=0.85\textwidth]{cv_pipeline}
\caption{Computer vision pipeline: frame capture, lens undistortion, resize to $640\times640$, TFLite inference, confidence filtering, and coordinate rescaling. The entire pipeline executes in 208\,ms on the Pi~5.}
\label{fig:cv_pipeline}
\end{figure}

\paragraph{Smart detection mode.} An optional \texttt{-{}-smart-detect} flag requires $k$ consecutive positive frames before triggering investigation (default $k=3$), suppressing transient false positives at a 0.6\,s delay.

\paragraph{Performance.} On the Pi~5 with XNNPACK CPU delegate: 206.5\,ms per frame (4.8\,FPS), 100\% detection rate, 0.966 mean confidence. At the nominal search speed of 8\,m/s (altitude-dependent schedule at 35\,m), adjacent frames overlap by approximately 95\% ($1 - 1.67/32.2$), providing 11--17 detection opportunities per target during a single flyover.

\subsection{Search Pattern Generation}\label{sec:search-pattern}

The boustrophedon (lawnmower) pattern was selected from three candidates---boustrophedon, spiral, and probabilistic---for its formal coverage guarantee~\cite{choset2001coverage}, predictable path length, and alignment with JSAR search protocols. Both lawnmower and spiral generators are implemented; all field missions use the lawnmower pattern for wide-area search.

\paragraph{Rotated-mask algorithm.}
The waypoint generator (\texttt{planning.py}) uses a rotate--rasterise--zigzag--rotate-back approach: (1)~rasterise the GPS polygon into a binary mask; (2)~rotate to align with the longest edge via the minimum-area bounding rectangle (rotating calipers), minimising U-turn count; (3)~compute strip spacing from the camera footprint; (4)~cast horizontal scan lines with $\tfrac{1}{3}$-strip inset to prevent boundary overshoot; (5)~optimise start corner for minimal transit; (6)~inverse-rotate to GPS coordinates. B\'{e}zier-smoothed U-turns maintain momentum through turns.

\paragraph{Coverage guarantee.}
The strip spacing is derived from the thin-lens ground footprint:
\begin{equation}\label{eq:footprint}
  W_g = \frac{w_s \cdot h}{f}, \qquad
  L = W_g\,(1 - \alpha)
\end{equation}
where $w_s = \SI{5.02}{\milli\metre}$ (IMX296 sensor width), $f = \SI{5.46}{\milli\metre}$ (calibrated focal length), $h$ is altitude, and $\alpha = 0.20$ is the overlap fraction. At $h = \SI{35}{\metre}$: $W_g \approx \SI{32.2}{\metre}$, $L \approx \SI{25.7}{\metre}$. Since $L < W_g$, consecutive swaths overlap by at least $\alpha \cdot W_g \approx \SI{6.4}{\metre}$, guaranteeing every ground point falls within at least one swath under \SIrange{2}{3}{\metre} GPS drift.

\paragraph{Scan angle optimisation.}
A 216-configuration parametric sweep (6~altitudes $\times$ 36~angles) confirmed the optimal scan angle at \SIrange{65}{75}{\degree}, consistent with the polygon's elongation. Deviating by \SI{30}{\degree} increases scan-line count by ${\sim}$\SI{40}{\percent}. The automatic angle from \texttt{cv2.minAreaRect} matches the optimum. Figure~\ref{fig:coverage_vs_time} shows the resulting near-linear coverage progression. A PLB-triggered focus area redirect generates a tighter pattern around the beacon signal with reduced speed (\SI{5}{\metre\per\second}).

\subsection{Mission State Machine}\label{sec:state-machine}

The 20-state FSM (Figure~\ref{fig:state_machine}, Appendix~\ref{app:states}) orchestrates the mission through four phases:

\begin{figure}[htbp]
\centering
\includegraphics[width=0.95\textwidth]{state_machine}
\caption{State transition diagram. Primary mission path flows left to right; engagement branches downward from SEARCH. Manual override (dashed) is accessible from any active state.}
\label{fig:state_machine}
\end{figure}

\begin{itemize}
    \item \textbf{Startup:} INIT $\to$ CONNECTING $\to$ ARMING (GPS fix $\geq$3D, $\geq$6 sats) $\to$ TAKEOFF.
    \item \textbf{Search:} PRE\_WAYPOINTS $\to$ TRANSIT\_TO\_SEARCH $\to$ SEARCH (lawnmower pattern with CV detection; PLB beacon redirect if timer expires).
    \item \textbf{Engagement:} CENTERING (fly to GPS estimate) $\to$ DESCENDING (reduce altitude for close-up view) $\to$ VERIFY (operator Y/N/I with 120\,s timeout; auto-reject resumes search) $\to$ APPROACH (7.5\,m offset) $\to$ HOVER\_TARGET (servo payload release). If the operator rejects or the timeout expires, RETURN\_TO\_SEARCH climbs back to search altitude and resumes the lawnmower pattern from the next unvisited waypoint.
    \item \textbf{Recovery:} RETURN\_TRANSIT $\to$ RETURN\_HOME $\to$ LANDING (triple touchdown detection) $\to$ DONE.
    \item \textbf{Override:} MANUAL mode is reachable from any active state via the M~key, RC switch, or geofence hard-cutoff. All autonomous commands cease; the pilot assumes full control. Re-entering autonomous mode requires an explicit resume command.
\end{itemize}

A detection queue with spatial deduplication (5\,m reject radius), bounded capacity (20 entries), and lazy validation manages multiple targets. Five independent safety mechanisms provide defence-in-depth: manual override, RC kill switch, RTL on link loss, three-layer geofence, and per-state timeouts.

\subsection{Target Localisation}\label{sec:localisation}

Each detection is converted from pixel coordinates to GPS using the pinhole camera model. The pixel offset from the image centre is projected to a body-frame displacement via the ground sampling distance (GSD $= w_s \cdot h / (f \cdot W)$), rotated into North--East coordinates using the drone's heading, and converted to latitude/longitude on the WGS\,84 ellipsoid. Multiple observations are fused through:

\begin{itemize}
    \item \textbf{Spatial clustering} (30\,m merge radius) for multi-target tracking;
    \item \textbf{Inverse-variance weighting} --- altitude factor $w_\mathrm{alt} = (h_\mathrm{ref}/h)^2$ and centrality factor $w_\mathrm{cen} = 1 + 4(1 - d/d_\mathrm{max})$;
    \item \textbf{Kalman filter} on the $[\phi, \lambda]$ state vector with measurement noise scaled by inverse observation weight, converging within 5--10 observations.
\end{itemize}

Video replay analysis (DJI flight footage, $1456 \times 1088$ at 30\,fps) yielded CEP$_{50}$ = 2.3\,m, maximum error = 16.5\,m (high-speed outlier). The characteristic directional elongation is attributed to GPS receiver latency (100--200\,ms), mitigated by multi-pass averaging in the lawnmower pattern.

\paragraph{Error budget.}
Six independent sources contribute to single-observation position uncertainty (Table~\ref{tab:error-budget-summary}). GPS receiver noise dominates at all altitudes; GPS timing lag is the largest \emph{systematic} contributor, displacing each estimate by $v_\mathrm{gnd} \cdot \Delta t$ along the flight heading. The RSS total of \SI{2.9}{\metre} at \SI{35}{\metre} altitude reduces to \SI{2.5}{\metre} with first-order velocity correction and further to sub-metre levels after inverse-variance fusion of 15+ observations across descent altitudes (Appendix~\ref{sec:error-budget}).

\subsection{Ground Station}\label{sec:groundstation}

The ground station is a browser-based dashboard served by a threaded HTTP server on the Pi at port~8090, accessible from any device on the local Wi-Fi network using the Pi's built-in wireless adapter. The operator needs only a standard web browser---no native application, no Mission Planner installation, and no platform dependency---yet receives live video, spatial awareness, and full command authority in a single view.

The dashboard provides three primary panels: (1)~a live MJPEG video stream with detection bounding boxes, confidence scores, and target ID overlays; (2)~a 2D GPS grid centred on the search area showing numbered detection clusters, the drone's current position, and the planned search path; and (3)~a command panel with nine buttons: arm, takeoff, investigate~(N), confirm target~(Y), mark as interest~(I), reject as false positive~(X), land, RTL, and manual override~(M). The operator workflow during engagement is: observe the detection cluster on the GPS grid, press~N to investigate, watch the live video as the drone centres and descends, then confirm~(Y) or reject~(X) based on the close-up view.

MJPEG was selected over H.264/WebRTC for three reasons: minimal client-side complexity (a single \texttt{<img>} tag), no transcoding load on the Pi's CPU, and graceful degradation on dropped frames (each frame is independently decodable). Measured end-to-end latency is approximately \SI{300}{\milli\second}.

Headless operation is auto-detected when no \texttt{DISPLAY} environment variable is set, enabling deployment over SSH without X11 forwarding. In this mode, all \texttt{cv2.imshow} calls are skipped and operator interaction occurs exclusively through the browser interface or terminal keypresses. A passive monitoring mode (\texttt{passive\_watch.py}) provides the same video stream and detection overlays but issues zero flight commands, enabling safe observation during manual RC flights.

\subsection{Simulation Framework}\label{sec:simulation}

Four simulation levels provide progressive fidelity: (1)~interactive simulator (keyboard flight over satellite map with ground-truth comparison); (2)~SITL integration (full ArduPilot autopilot with simulated camera view); (3)~SITL with real webcam; (4)~DJI video replay with synchronised SRT telemetry. The same detection model, GPS estimation mathematics, and MAVLink command interface are used at every level, so transitioning to real hardware requires only configuration changes. Bugs caught in simulation include a MAVLink race condition during takeoff, incorrect latitude scaling, auto-disarm timeout, and GPS timing lag.
