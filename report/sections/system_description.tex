\section{System Description}\label{sec:sysdesc}

With the design rationale established (Section~\ref{sec:rationale}), this section describes how those choices are realised in the final system. The platform integrates seven subsystems: a hardware airframe with companion computer (\S\ref{sec:hw}), eleven Python modules (\S\ref{sec:sw-arch}), a YOLOv8n vision pipeline at 4.8\,FPS (\S\ref{sec:cv}), a boustrophedon search pattern with formal coverage guarantee (\S\ref{sec:search-pattern}), a 20-state mission FSM with six independent safety layers (\S\ref{sec:state-machine}), GPS target localisation at CEP$_{50}$ = 2.3\,m (\S\ref{sec:localisation}), and a browser-based ground station at \SI{300}{\milli\second} video latency (\S\ref{sec:groundstation}). The design philosophy is \emph{independent modules composed at runtime}: vision, planning, geofencing, and navigation have zero mutual dependencies, enabling isolated testing and single-file swaps. Figure~\ref{fig:mission_overview} shows the complete mission plan overlaid on the Fenswood Farm site.

The Pi communicates with the Cube via UART at 921\,600\,baud through a MAVProxy bridge, which republishes MAVLink traffic on two outputs: UDP port~14550 (Python mission code) and TCP port~5762 (Mission Planner via Wi-Fi). This decouples the flight controller from the companion computer---any component can restart independently, and the same MAVLink stream serves both monitoring and commanding without message contention (Appendix~\ref{sec:streaming-arch}). The camera captures $1456 \times 1088$ global-shutter frames via CSI-2 at up to 30\,fps (throttled by inference to ${\sim}$4.8\,fps); lens distortion is corrected using precomputed \texttt{cv2.remap} matrices (calibrated RMS = 0.399\,px, $+$1.5\,ms overhead; Appendix~\ref{sec:calibration}). The calibrated focal length is \SI{5.46}{\milli\metre}, yielding a HFOV of ${\approx}\,49.3^{\circ}$. The global shutter eliminates rolling-shutter distortion during flight, preserving accurate bounding-box geometry for GPS estimation.

Eleven Python modules totalling approximately 4\,400 lines of production code are organised in four layers (Figure~\ref{fig:architecture}). \begin{itemize}
    \item \textbf{Configuration layer:} \texttt{config.py} centralises all 40+ tuneable parameters with auto-detection of connection strings and platform (Appendix~\ref{app:config}); \texttt{states.py} defines the 20-state enumeration.
    \item \textbf{Independent modules:} \texttt{vision.py} exposes a single function \texttt{detect\_in\_image(frame)} $\to$ \texttt{(found, cx, cy, conf)}, encapsulating camera setup, backend selection, and all preprocessing. \texttt{planning.py} takes a GPS polygon and returns an ordered list of waypoints. \texttt{gps\_utils.py} provides bidirectional GPS$\leftrightarrow$pixel coordinate transforms via \texttt{GeoTransformer}. \texttt{geofence.py} enforces NFZ boundaries. These four modules import only \texttt{config.py} and standard libraries---no mutual dependencies---enabling isolated unit testing (127 tests) and single-file replacement.
    \item \textbf{Domain modules:} \texttt{navigation.py} wraps MAVLink commands (Table~\ref{tab:mavlink-commands}) with altitude clamping and ACK handling; \texttt{stream\_server.py} serves the MJPEG ground station.
    \item \textbf{Orchestration layer:} \texttt{state\_machine.py} implements all 20 state handlers as a mixin class consumed by \texttt{main.py}, which composes the modules and runs the main loop at ${\sim}$20--50\,Hz (limited by inference when CV is active).
\end{itemize}

The \texttt{navigation.py} module enforces a hard 50\,m altitude cap on all commanded altitudes (R04), rejecting and clamping any request that exceeds this limit regardless of the calling state. The data pipeline traverses five stages per main-loop iteration (Figure~\ref{fig:pi_system}): (1)~capture a frame and apply lens undistortion via precomputed remap matrices; (2)~resize to $640\times640$, normalise to float32, and run YOLOv8n inference (${\sim}$208\,ms); (3)~convert the pixel detection to a GPS estimate using the pinhole camera model (\S\ref{sec:localisation}); (4)~dispatch the current state handler, which may issue MAVLink commands via \texttt{navigation.py}; and (5)~enforce geofence constraints. Geofencing always runs \emph{after} the state handler, so any waypoint commands can be overridden by repulsive velocities or emergency RTL.

\paragraph{Geofence enforcement.}
The geofence module implements five independent protection layers (Figure~\ref{fig:geofence_diagram}). The outermost layer is the \textbf{Flight Area boundary}: a four-vertex polygon checked via \texttt{cv2.pointPolygonTest} every main-loop iteration (${\sim}$20--50\,Hz); any excursion triggers an immediate emergency RTL with no buffer or warning zone. The remaining four layers protect the \textbf{SSSI no-fly zone}: (1)~plan-time waypoint filtering removes any waypoint within 30\,m of the boundary; (2)~a speed scalar field that linearly decelerates the drone from full speed at the 8\,m soft boundary to a full stop at the 3\,m hard boundary; (3)~a repulsive potential field that applies an inverse-distance velocity correction to deflect the aircraft away from the nearest boundary edge; and (4)~a hard cutoff that forces MANUAL mode if the drone enters the SSSI polygon. All distance computations use \texttt{cv2.pointPolygonTest} for signed distance in a local pixel coordinate frame (via \texttt{GeoTransformer}), then convert back to GPS. The repulsive offset is applied as a velocity correction \emph{after} the state handler's waypoint command, ensuring no state can inadvertently fly into restricted airspace (see Appendix~\ref{sec:repulsive-field} for vector field mathematics and Appendix~\ref{sec:nfz-interaction} for NFZ margin analysis).

\subsection{Computer Vision Pipeline}\label{sec:cv}

The vision subsystem resides in \texttt{vision.py}, exposing a single interface: \texttt{detect\_in\_image(frame)} $\to$ \texttt{(found, cx, cy, confidence)}. The pipeline proceeds as follows:

\paragraph{Preprocessing.} Lens undistortion (if calibration data are available), colour-space handling (the IMX296 outputs BGR despite its RGB888 label---no conversion applied), resize from $1456\times1088$ to $640\times640$ via bilinear interpolation, and float32 normalisation ($[0,255] \to [0,1]$), yielding input tensor $[1, 640, 640, 3]$.

\paragraph{Inference.} The TFLite model produces output tensor $[1, 5, 8400]$ (8400 anchor-free candidates across three feature pyramid scales at $8\times$, $16\times$, and $32\times$ downsampling). Postprocessing applies confidence filtering (threshold 0.4), greedy best-detection selection (single highest-confidence target per frame), and coordinate rescaling to original frame dimensions. A pixel-coordinate heuristic (threshold $>1.5$) auto-detects whether the model returns normalised or absolute coordinates, handling both TFLite and NCNN output conventions without manual configuration. The Ultralytics backend handles non-maximum suppression (NMS) internally; the TFLite backend implements equivalent greedy filtering in \texttt{vision.py}.

\paragraph{Three backends.} The system supports Ultralytics~\cite{yolov8} (development laptop) and TFLite~\cite{tflite} (production Pi), with an NCNN~\cite{ncnn} backend implemented but not yet validated on the Pi. Backend selection is automatic at import time. Both validated backends consume the same model weights and produce identical detection semantics (Appendix~\ref{app:cv-extended}).

\begin{figure}[ht]
\centering
\includegraphics[width=0.85\textwidth]{cv_pipeline}
\caption{Computer vision pipeline: frame capture, lens undistortion, resize to $640\times640$, TFLite inference, confidence filtering, and coordinate rescaling. The entire pipeline executes in 208\,ms on the Pi~5.}
\label{fig:cv_pipeline}
\end{figure}

\paragraph{Smart detection mode.} An optional \texttt{-{}-smart-detect} flag requires $k$ consecutive positive frames before triggering investigation (default $k{=}3$), suppressing transient false positives at the cost of a 0.6\,s delay.

\paragraph{Performance.} On the Pi~5 with XNNPACK CPU delegate: 206.5\,ms per frame (4.8\,FPS), 100\% detection rate (50/50 bench frames), 0.966 mean confidence (Appendix~\ref{app:cv:benchmarks}). The model was retrained three times---at $640$, $1280$, and $1088$\,px---with the final v2 model achieving mAP$_{50}$ = 0.995 on a dataset of 300 synthetic, 16 real, and 50 negative images (Appendix~\ref{app:cv:training}). Search speed is altitude-dependent (6\,m/s at 20\,m, linearly increasing to 10\,m/s at 50\,m); at the nominal \SI{35}{\metre} altitude this yields ${\approx}$\,8.7\,m/s. At 4.8\,FPS, adjacent frames overlap by approximately 94\%, providing 11--17 detection opportunities per target during a single flyover (speed--detection trade-off analysis in Appendix~\ref{app:cv:speed}).

\subsection{Search Pattern Generation}\label{sec:search-pattern}

The boustrophedon (lawnmower) pattern~\cite{choset2001coverage} is implemented via a rotate--rasterise--zigzag--rotate-back algorithm in \texttt{planning.py}: the GPS polygon is rasterised into a binary mask, rotated to align with the longest edge (minimising U-turns), stripped at camera-footprint spacing, and inverse-rotated back to GPS coordinates. B\'{e}zier-smoothed U-turns maintain momentum.

\paragraph{Coverage guarantee.}
Strip spacing derives from the thin-lens footprint: $W_g = w_s \cdot h / f$, lane spacing $L = W_g(1 - \alpha)$. At \SI{35}{\metre}: $W_g \approx \SI{32.2}{\metre}$, $L \approx \SI{25.7}{\metre}$ (20\% overlap), guaranteeing every ground point falls within at least one swath under \SIrange{2}{3}{\metre} GPS drift. A 216-configuration sweep confirmed the optimal scan angle at \SIrange{65}{75}{\degree} (Appendix~\ref{sec:path-opt}). Figure~\ref{fig:coverage_vs_time} shows near-linear coverage progression.

\subsection{Mission State Machine}\label{sec:state-machine}

The 20-state FSM (Figure~\ref{fig:state_machine}, Appendix~\ref{app:states}) orchestrates the mission through four phases:

\begin{figure}[htbp]
\centering
\includegraphics[width=0.95\textwidth]{state_machine}
\caption{State transition diagram. Primary mission path flows left to right; engagement branches downward from SEARCH. Manual override (dashed) is accessible from any active state.}
\label{fig:state_machine}
\end{figure}

\begin{itemize}
    \item \textbf{Startup:} INIT $\to$ CONNECTING $\to$ ARMING (GPS fix $\geq$3D, $\geq$6 sats) $\to$ TAKEOFF.
    \item \textbf{Search:} PRE\_WAYPOINTS $\to$ TRANSIT\_TO\_SEARCH $\to$ SEARCH (lawnmower pattern with CV detection; PLB beacon redirect if timer expires).
    \item \textbf{Engagement:} CENTERING (fly to GPS estimate) $\to$ DESCENDING (reduce altitude for close-up view) $\to$ VERIFY (operator Y/N/I with 120\,s timeout; auto-reject resumes search) $\to$ APPROACH (7.5\,m offset) $\to$ HOVER\_TARGET (servo payload release). If the operator rejects or the timeout expires, RETURN\_TO\_SEARCH climbs back to search altitude and resumes the lawnmower pattern from the next unvisited waypoint.
    \item \textbf{Recovery:} RETURN\_TRANSIT $\to$ RETURN\_HOME $\to$ LANDING (triple touchdown detection) $\to$ DONE.
    \item \textbf{Override:} MANUAL mode is reachable from any active state via the M~key, RC switch, or geofence hard-cutoff. All autonomous commands cease; the pilot assumes full control. Re-entering autonomous mode requires an explicit resume command.
\end{itemize}

A detection queue with spatial deduplication (5\,m reject radius against all rejected targets and items of interest), bounded capacity (20 entries, oldest-first eviction), and lazy validation manages multiple targets without revisiting previously-investigated locations.

\paragraph{Safety mechanisms.}
Six independent layers provide defence-in-depth:
\begin{enumerate}[nosep]
    \item \textbf{RC override guard} --- checked \emph{before} every state dispatch and key handler; if the pilot switches away from GUIDED mode, all autonomous commands cease immediately and the code enters a guard loop until mode is restored (modes 4/GUIDED, 6/RTL, and 9/LAND are permitted).
    \item \textbf{RC kill switch} --- switching the transmitter to STABILIZE/LOITER bypasses all software; the pilot has direct control.
    \item \textbf{GPS fix monitoring} --- continuous checks for fix type $\geq$3D and satellite count $\geq$6; sustained degradation triggers emergency RTL.
    \item \textbf{Flight Area boundary} --- \texttt{cv2.pointPolygonTest} on the four-vertex flight area polygon every iteration; any excursion triggers immediate RTL.
    \item \textbf{Five-layer SSSI geofence} --- plan-time filtering, speed ramp, repulsive field, and hard cutoff (\S\ref{sec:sw-arch}).
    \item \textbf{Per-state timeouts} --- each state has a configurable maximum duration (e.g.\ VERIFY: 120\,s); expiry triggers the fallback transition (typically RETURN\_TO\_SEARCH). ArduCopter's own GCS failsafe (\texttt{FS\_GCS\_ENABLE}) provides a hardware-level backstop if the companion computer link is lost entirely.
\end{enumerate}
Appendix~\ref{app:states} lists all 20~states with their entry conditions, exit transitions, and timeout values.

\subsection{Target Localisation}\label{sec:localisation}

Each detection converts from pixel coordinates to GPS using the pinhole camera model. The pixel offset $(\Delta u, \Delta v)$ from the image centre projects to a body-frame displacement via the ground sampling distance:
\begin{equation}\label{eq:gsd-sysdesc}
  \mathrm{GSD} = \frac{w_s \cdot h}{f \cdot W},\qquad
  d_x = \Delta u \cdot \mathrm{GSD},\quad
  d_y = \Delta v \cdot \mathrm{GSD}
\end{equation}
where $w_s = \SI{5.02}{\milli\metre}$ is the sensor width, $f = \SI{5.46}{\milli\metre}$ the calibrated focal length, $h$ the barometric altitude, and $W = 1456$\,px the image width. The body-frame displacement $(d_x, d_y)$ is rotated into North--East coordinates using the drone's heading and converted to latitude/longitude on the WGS\,84 ellipsoid. Appendix~\ref{sec:gps-deep} documents the full 15-stage pipeline with flowchart, error budget by flight phase, and roll/pitch geometry analysis (Figure~\ref{fig:pipeline-flow}). Multiple observations are fused through:

\begin{itemize}
    \item \textbf{Spatial clustering} (30\,m merge radius) for multi-target tracking;
    \item \textbf{Inverse-variance weighting} --- altitude factor $w_\mathrm{alt} = (h_\mathrm{ref}/h)^2$ and centrality factor $w_\mathrm{cen} = 1 + 4(1 - d/d_\mathrm{max})$;
    \item \textbf{Kalman filter} on the $[\phi, \lambda]$ state vector with measurement noise scaled by inverse observation weight, converging within 5--10 observations.
\end{itemize}

Video replay analysis (DJI flight footage, $1456 \times 1088$ at 30\,fps) yielded CEP$_{50}$ = 2.3\,m and a maximum error of 16.5\,m (high-speed outlier). The directional elongation stems from GPS receiver latency (100--200\,ms), which multi-pass averaging partially mitigates. Six independent error sources contribute to a single-observation RSS uncertainty of \SI{2.9}{\metre} at \SI{35}{\metre} altitude, dominated by GPS receiver noise (\SI{2.3}{\metre}) and timing lag (\SI{1.5}{\metre}). After inverse-variance fusion of 15+ multi-altitude observations, the fused estimate converges to sub-metre accuracy, exceeding the 5--10\,m landing requirement (R07) with $>$99\% probability. Appendix~\ref{sec:gps-deep} provides the full error budget, convergence plots, and fusion strategy comparison.

\subsection{Ground Station}\label{sec:groundstation}

The ground station is a browser-based dashboard served by a \texttt{ThreadingMixIn} HTTP server on the Pi at port~8090, accessible from any device on the local Wi-Fi network. It provides three panels: (1)~live MJPEG video stream with detection bounding-box overlays and telemetry text; (2)~2D GPS grid showing detection clusters, drone position, and search path coverage; and (3)~command buttons (investigate~N, confirm~Y, reject~X, interest~I, land~L, RTL, manual override~M). The operator's Y/N decision at the VERIFY stage is the only human input required during the mission. Commands are sent via an \texttt{/cmd?key=} HTTP endpoint, enabling both browser interaction and programmatic control. MJPEG was chosen over H.264/WebRTC for its minimal client complexity (single \texttt{<img>} tag), zero transcoding load, and per-frame decodability---important given the Pi's limited CPU budget after inference. Measured latency is \SI{300}{\milli\second} at \SI{0.3}{\mega\byte\per\second}. The Pi auto-detects headless operation (no \texttt{DISPLAY}), enabling SSH deployment without X11 forwarding; a terminal keyboard input thread provides the same key bindings over PuTTY (Appendix~\ref{sec:streaming-arch}).

\subsection{Simulation Framework}\label{sec:simulation}

Four simulation levels provide progressive fidelity (Appendix~\ref{sec:sim-validation}): (1)~interactive simulator (\texttt{simple\_simulator.py}: keyboard flight over satellite map with ground-truth GPS comparison); (2)~SITL integration (full ArduPilot autopilot with simulated camera view, testing the real MAVLink command path); (3)~SITL with real webcam (validates CV on live video without flight risk); and (4)~DJI video replay with synchronised SRT telemetry (30\,fps frame-accurate altitude and GPS, calibrating detection altitude and GPS estimation accuracy). All four levels share the same \texttt{vision.py} model, \texttt{gps\_utils.py} estimation mathematics, and \texttt{navigation.py} MAVLink interface, so transitioning to real hardware requires only a configuration change (\texttt{DRONE\_MODE=REAL}). Simulation alone caught 12 defects---including a \texttt{SET\_POSITION\_TARGET} race condition that cancelled \texttt{NAV\_TAKEOFF}, an incorrect latitude-scaling constant ($\cos\phi$ omitted from longitude conversion), a 10-second auto-disarm timeout (\texttt{DISARM\_DELAY}), and GPS receiver timing lag causing 1\,m directional bias at 5\,m/s---all resolved before any hardware integration.
