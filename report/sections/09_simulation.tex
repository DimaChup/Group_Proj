\section{Simulation Framework}\label{sec:simulation}

Autonomous SAR drone development presents a fundamental tension: algorithms must be validated extensively before flight, yet real flights are expensive, weather-dependent, and risk hardware loss. A multi-fidelity simulation framework was therefore developed to enable iterative refinement of the detection, estimation, and landing algorithms entirely on a laptop before any outdoor testing.

\subsection{Multi-Fidelity Approach}\label{sec:sim-fidelity}

The project employs four simulation levels of increasing fidelity, following the simulation-first methodology advocated for robotic systems where hardware access is intermittent or costly~\cite{shah2018}:

\begin{enumerate}
    \item \textbf{Level~1: Interactive simulator} (\texttt{simple\_simulator.py}). A self-contained environment where the operator flies a virtual drone over a satellite image using keyboard controls. The same YOLOv8n model runs inference on a synthetically generated camera view. No autopilot software is required---MAVLink telemetry is simulated internally. This level tests the GPS estimation pipeline, multi-target clustering, visual servoing, and landing sequence with full ground-truth comparison.

    \item \textbf{Level~2: SITL with simulated camera} (\texttt{simulation.py} feeding \texttt{main.py}). ArduPilot's Software-in-the-Loop (SITL) runs the full autopilot firmware on the laptop~\cite{ardupilot2024}. The mission orchestrator issues MAVLink commands identical to those used in flight, while \texttt{simulation.py} extracts a FOV-correct camera subimage from the satellite map at the drone's current position and altitude. This level validates the complete state machine---arming, takeoff, guided navigation, geofence enforcement, and landing---against a realistic autopilot model with simulated GPS noise and vehicle dynamics.

    \item \textbf{Level~3: SITL with real webcam}. The same SITL autopilot runs, but the camera source switches to a physical webcam pointed at a printed dummy. This exercises the vision pipeline under real optical conditions---lighting variation, lens distortion, motion blur---while keeping the flight controller in simulation. Setting \texttt{DRONE\_MODE=REAL} routes frames from the webcam instead of the satellite map.

    \item \textbf{Level~4: Video replay} (\texttt{video\_test.py}). Recorded DJI flight footage is replayed frame-by-frame with the detection model running on each frame. SRT telemetry files provide per-frame GPS coordinates, altitude, and heading, enabling the full pixel-to-GPS estimation pipeline to run on real aerial imagery. This level bridges the sim-to-real gap by exercising the vision system against genuine outdoor conditions---sun glare, shadows, varied terrain textures, real target appearance---without requiring a live flight.
\end{enumerate}

Each level shares the same detection model (\texttt{best.tflite}), the same GPS estimation mathematics, and the same MAVLink command interface where applicable. Bugs found at Level~1 do not require re-testing at higher levels; only the camera source and vehicle dynamics change.

\subsection{Interactive Simulator}\label{sec:sim-interactive}

The interactive simulator (\texttt{simple\_simulator.py}, 2508~lines) provides a comprehensive test environment for the GPS estimation and target approach algorithms. The operator controls the virtual drone via keyboard: WASD for lateral movement, R/F for altitude, Q/E for yaw. Six operational modes are available through single-key activation:

\begin{itemize}
    \item \textbf{Manual flight} (WASD): flyover detection sweeps across the search area.
    \item \textbf{GPS centering} (C~key): the drone navigates to the current best GPS estimate of the target, derived from accumulated pixel-to-GPS observations.
    \item \textbf{Visual servo} (V~key): proportional control centres the target in the camera frame using pixel error, with exponential moving average smoothing ($\alpha = 0.3$) to reject jitter. Speed is clamped and the controller falls back to the last GPS estimate if the target is temporarily lost.
    \item \textbf{GPS lock} (G~key): while visually centred, the drone's GPS position is averaged over 30~seconds to produce a high-accuracy target coordinate. Only centre-snap samples---where the target lies within 30\,px of the frame centre---are accepted.
    \item \textbf{Investigate} (N~key): three-phase sequence (approach, descend to 15\,m, observe) during which the operator classifies the target as confirmed dummy~(Y), item of interest~(I), or false positive~(X).
    \item \textbf{Offset landing} (L~key): the drone flies to a point 7.5\,m north of the locked GPS estimate, descends, and lands autonomously.
\end{itemize}

Three GPS estimators run concurrently on each detection cluster: a rolling weighted average of the most recent 50~observations, a cumulative weighted average over all observations, and a two-dimensional Kalman filter with measurement noise scaled by inverse observation weight. Each observation is weighted by an altitude-dependent factor $w_{\text{alt}} = (30/h)^2$, reflecting the improved ground sample distance at lower altitudes, multiplied by a centre-proximity weight. All three estimators are compared against ground truth in real time.

\subsubsection{Configurable Error Injection}

A critical feature of the simulator is its ability to inject realistic sensor noise through command-line flags and real-time sliders, allowing systematic study of algorithm robustness:

\begin{itemize}
    \item \textbf{GPS drift} (\texttt{-{}-gps-drift $N$}): applies an Ornstein--Uhlenbeck random walk to the reported GPS position, producing temporally correlated drift that mimics real receiver behaviour rather than independent white noise. With $N = 3$, the standard deviation matches typical open-sky GPS accuracy ($\sim$2--3\,m).

    \item \textbf{Camera shake} (\texttt{-{}-shake $N$}): introduces altitude-dependent angular camera jitter simulating motor vibration. The HUD displays the ground-plane equivalent (e.g., ``SHAKE: 5\,px = 20\,cm on ground'') so the operator can assess real-world impact on detection confidence.

    \item \textbf{Inference throttle} (\texttt{-{}-fps $N$}): limits CV inference to $N$~frames per second, matching the Raspberry~Pi's measured 4.8\,FPS throughput. This reveals whether the detection rate is sufficient to catch a target during a flyover at 3--5\,m/s.

    \item \textbf{Additional noise sources}: altitude noise (\texttt{-{}-alt-noise}), yaw compass jitter (\texttt{-{}-yaw-noise}), and systematic FOV calibration error (\texttt{-{}-fov-error}) can be combined to stress-test the estimation pipeline under worst-case conditions.
\end{itemize}

Seven real-time sliders in an auxiliary window allow these parameters to be adjusted mid-flight without restarting, enabling rapid sensitivity analysis across the noise parameter space.

\subsubsection{Bullseye Scatter Plots and Ground-Truth Comparison}

The simulator's bottom-left panel displays a GPS estimation scatter plot that provides immediate visual feedback on estimator performance (Figure~\ref{fig:simulator}). Each observation is plotted as a coloured dot relative to the ground-truth target position, with concentric circles at 1\,m, 2\,m, and 5\,m radii forming a bullseye pattern. Error ellipses computed from the observation covariance are overlaid in real time. The three estimators---rolling average (blue), cumulative average (green), and Kalman filter (red)---are displayed simultaneously, allowing direct visual comparison of convergence behaviour. When offset landing is active, the plot also shows the 7.5\,m landing zone and the actual touchdown point, providing an immediate assessment of end-to-end accuracy. At session end, matplotlib charts display the complete estimate history and a per-estimator error summary.

\subsubsection{Multi-Target and Spatial Clustering}

Multiple dummy targets can be placed interactively on the satellite map before each run. The simulator implements spatial clustering with a configurable merge radius (\texttt{-{}-cluster-dist}, default 30\,m): detections within this radius of an existing cluster are routed to that cluster and update its estimators; detections beyond this radius spawn a new cluster with a permanent~ID. Each cluster maintains independent rolling, cumulative, and Kalman estimators, enabling testing of scenarios with multiple casualties, false-positive rejection, and cluster disambiguation through the pilot classification workflow (Y/I/X).

\subsubsection{End-to-End Mission Testing}

The full operational sequence can be exercised without any real hardware:

\begin{enumerate}
    \item Fly manually over the search area; the AI detects the dummy during flyover and accumulates GPS observations ($\sim$1--3\,m initial error from altitude).
    \item Press C to auto-navigate to the GPS estimate; the drone converges on the target cluster.
    \item Descend to 10\,m; press V to engage visual servo, which centres the target in-frame to sub-metre precision using direct pixel feedback.
    \item Press G to begin a 30-second GPS lock, collecting centre-snap samples while the visual servo maintains alignment; final estimate error typically reaches ${\sim}0.5$\,m.
    \item Press L to execute offset landing: the drone flies 7.5\,m north of the locked estimate, descends, and touches down.
    \item Press ESC to view the post-flight summary: estimate error, landing distance from target, and scatter plot analysis.
\end{enumerate}

This sequence was run hundreds of times during development, validating the estimation pipeline and landing logic under varying noise conditions before any outdoor flight.

\subsection{SITL Integration}\label{sec:sim-sitl}

At Level~2, ArduPilot SITL replaces the keyboard-driven flight model with a full autopilot simulation. SITL runs the same C++ firmware as the Cube Orange+ flight controller, modelling vehicle dynamics, GPS receiver behaviour, barometric altitude, and RC input~\cite{ardupilot2024}. The mission orchestrator connects via MAVLink over UDP (port~14550) and issues identical commands to those used in real flight: \texttt{MAV\_CMD\_NAV\_TAKEOFF}, guided waypoint navigation via \texttt{SET\_POSITION\_TARGET\_GLOBAL\_INT}, mode changes, and \texttt{MAV\_CMD\_NAV\_LAND}. Mission Planner connects simultaneously via a TCP bridge (port~5762) for monitoring and parameter adjustment.

The SITL home location is set to the actual flight site coordinates (\SI{51.423406}{\degree}N, \SI{2.671446}{\degree}W), ensuring that the lawnmower search pattern, geofence boundaries, and SSSI no-fly zone are tested with real-world geometry. SITL's simulated GPS noise (${\sim}0.5$\,m) is smaller than real conditions (${\sim}2$--3\,m), but provides a baseline for verifying navigation logic.

\subsection{Simulated Camera View}\label{sec:sim-camera}

The \texttt{SimulationEnvironment} class in \texttt{simulation.py} generates a synthetic camera frame at each timestep by extracting a subimage from a georeferenced satellite photograph (\texttt{map.jpg}). Given the drone's pixel position $(c_x, c_y)$, altitude $h$, and yaw angle $\psi$, the visible ground footprint is computed from the camera's calibrated field of view:

\begin{equation}
    w_{\text{ground}} = 2h \tan\!\left(\frac{\text{FOV}_h}{2}\right), \qquad \text{FOV}_h = 2\arctan\!\left(\frac{w_{\text{sensor}}}{2f}\right)
\end{equation}

\noindent where $w_{\text{sensor}} = 5.02$\,mm and $f = 5.46$\,mm are the calibrated sensor width and focal length. The corresponding map region is extracted with edge padding, rotated by the yaw angle using an affine transform, cropped to the camera aspect ratio ($1456 \times 1088$), and resized to the inference resolution. A dummy image (\texttt{dummy.png}) with alpha-channel transparency is composited at the correct position and altitude-dependent scale, producing a frame that the YOLOv8n model processes identically to a real camera capture. Multiple targets can be placed interactively on the map before each run.

This approach ensures that the detection model is exercised against realistic background textures (grass, paths, shadows) at altitude-correct scales, rather than against synthetic uniform backgrounds that would inflate detection performance.

\subsubsection{Perspective Camera Rendering}

When the \texttt{-{}-sim-tilt} flag is active, the simulated camera accounts for the drone's pitch and roll as reported by SITL telemetry.  For each output pixel corner, a ray is cast from the camera through the image plane onto the ground plane ($z = 0$) using the full rotation matrix $\mathbf{R} = \mathbf{R}_z(\psi)\,\mathbf{R}_y(-\theta)\,\mathbf{R}_x(-\phi)$, where $\psi$, $\theta$, and $\phi$ are the yaw, pitch, and roll angles respectively.  The four ground-plane intersections define a trapezoid on the satellite map; an \texttt{OpenCV} perspective warp maps this trapezoid into the rectangular output frame.  Target assets are composited onto the map region \emph{before} the warp, so they receive the same perspective distortion as the terrain.  If any corner ray points upward (camera tilted past the horizon), the renderer falls back to the nadir view.

This perspective rendering allows the simulation to \emph{generate} the attitude-dependent camera tilt problem and simultaneously \emph{verify} the ray-tracing GPS compensation (Section~\ref{sec:tilt-compensation}), since both use identical rotation mathematics---providing a closed-loop validation of the tilt correction that would otherwise require flight data.

\subsubsection{Configurable Sensor Degradation at Level~2}

Beyond the interactive simulator's error injection (Section~\ref{sec:sim-interactive}), the SITL level supports three CLI flags that degrade the synthetic camera view to approximate real-world conditions:

\begin{itemize}
    \item \texttt{-{}-blur $F$}: applies physics-based directional motion blur.  A one-dimensional kernel is oriented along the yaw angle, sized by the root-sum-square of translational blur (ground speed $\times$ exposure time / GSD) and rotational blur (yaw rate $\times$ focal length in pixels $\times$ exposure time), scaled by factor $F$.  The kernel is capped at 51\,px.
    \item \texttt{-{}-shake $N$}: adds a random per-frame pixel translation of $\pm N$\,px in both axes, simulating motor vibration.
    \item \texttt{-{}-noise $L$}: injects Gaussian noise into the GPS position ($\sigma \approx 2.8L$\,m), altitude ($\sigma = 0.5L$\,m), and attitude angles ($\sigma \approx 0.5L^{\circ}$), modelling degraded sensor conditions.
\end{itemize}

\noindent These flags allow the SITL simulation to stress-test detection reliability and GPS estimation accuracy under conditions closer to real flight, complementing the interactive simulator's error injection with the full autopilot dynamics provided by ArduPilot SITL.

\subsection{Video Replay Tool}\label{sec:sim-video}

The video replay tool (\texttt{video\_test.py}) provides the highest-fidelity offline validation by running the detection model on recorded DJI flight footage. Each video frame is paired with its corresponding SRT telemetry entry, providing GPS coordinates, barometric altitude, and heading at 30\,fps resolution. The tool runs the full pixel-to-GPS estimation pipeline on each detection, accumulating observations, updating the Kalman filter, and building the same scatter plots used in the interactive simulator.

Key features include a scale bar calibrated to the current altitude and FOV, a right-click measurement tool that reports ground distances in metres, and a side-by-side model comparison mode (\texttt{video\_test\_compare.py}) that toggles between two models on the same frame with a single keypress. The FOV was calibrated specifically for the cropped DJI video camera ($\text{HFOV} = \SI{54.4}{\degree}$ at $1456 \times 1088$, distinct from the onboard Pi IMX296 HFOV of $49.3^{\circ}$) by clicking the top and bottom of the dummy at nine different altitudes using a dedicated calibration tool.

Analysis of 6854~frames from a real flight revealed a GPS timing lag of 100--200\,ms in the receiver, causing a ${\sim}1$--$1.6$\,m systematic offset along the direction of travel at typical search speeds. This finding---which would have been nearly impossible to diagnose during a live flight---led to the identification of speed-dependent bias in the estimation pipeline and informed the design of the multi-pass averaging strategy described in Section~\ref{sec:localisation}.

\subsection{Simulation-to-Real Transfer}\label{sec:sim-transfer}

A central design goal is that the transition from simulation to real hardware requires no code changes---only configuration changes---an approach consistent with digital twin methodology in UAV development~\cite{jones2020}. Three mechanisms enable this:

\begin{enumerate}
    \item \textbf{Configuration auto-detection.} At import time, \texttt{config.py} probes for a serial connection to the Cube flight controller. If found, the system operates in real mode; otherwise, it connects to SITL via UDP. The \texttt{DRONE\_MODE} environment variable provides an explicit override. Camera selection follows the same pattern: picamera2 on the Pi, OpenCV \texttt{VideoCapture} on the laptop.

    \item \textbf{Identical state machine.} The mission orchestrator (\texttt{main.py}) contains no conditional branches distinguishing simulation from real flight. The 20-state finite state machine---arming, takeoff, search pattern execution, detection-triggered transitions, operator verification, and landing---runs the same logic in both environments. Only the camera frame source and MAVLink endpoint differ.

    \item \textbf{Same model weights.} All platforms load the same \texttt{best.tflite} model file with input shape $[1, 640, 640, 3]$ and output shape $[1, 5, 8400]$. The vision module applies identical preprocessing (resize, normalise, optional lens undistortion) regardless of frame origin.
\end{enumerate}

\subsubsection{What Transfers Well}

State machine logic, GPS estimation mathematics, geofence enforcement, and the MAVLink command interface transferred from simulation to the real Cube without modification. The lawnmower search pattern, tested hundreds of times against the actual site polygon in SITL, executed correctly on the first outdoor attempt. Operator workflows---target classification, verification prompts, manual override---were rehearsed extensively in the simulator before being needed in the field.

\subsubsection{Known Sim-to-Real Gaps}

Detection reliability is the primary gap: a model trained on synthetic composites may underperform against real lighting, motion blur, and non-ideal target poses. Wind effects on flight stability and their interaction with visual servoing cannot be reproduced at Levels~1--2. GPS accuracy in simulation (${\sim}0.5$\,m SITL noise) is optimistic relative to real conditions (${\sim}2$--3\,m). These gaps are addressed by the progressive testing methodology described in Section~\ref{sec:testing}, where passive flight logging validates detection performance before autonomous operation is enabled.

\subsection{Bugs Caught in Simulation}\label{sec:sim-bugs}

The simulation framework identified several issues that would have been dangerous or costly to discover during flight:

\begin{itemize}
    \item A MAVLink command race condition where \texttt{SET\_POSITION\_TARGET} commands issued during takeoff cancelled the \texttt{NAV\_TAKEOFF} command, leaving the drone in an intermediate state.
    \item An incorrect latitude scaling factor in the geo-transformer that introduced a systematic northward bias in all GPS estimates, discovered by comparing scatter plots against ground truth in the interactive simulator.
    \item The need for camera warm-up frames to avoid initial dark exposures on the Pi's IMX296 sensor.
    \item An auto-disarm timeout (\texttt{DISARM\_DELAY=10}) in ArduPilot that caused the drone to disarm on the ground before the mission script could complete arming, resolved by setting the parameter to zero.
    \item A GPS timing lag of 100--200\,ms causing directional bias in target estimates at speed, discovered through video replay analysis of DJI footage.
\end{itemize}

Each issue was resolved in simulation at zero cost and zero risk, avoiding time-pressured debugging in the field. The multi-fidelity approach---from keyboard-driven sandbox to recorded flight footage---provided confidence that the algorithms were sound before committing to outdoor testing.
